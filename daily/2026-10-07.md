# CV Digest — Wednesday, October 7, 2026

## TL;DR
- **PyTorch moves media decoding to TorchCodec.** `torchvision.io.read_video` and `VideoReader` are deprecated, so any video data loader that still uses them needs a migration plan.
- **CUDA green contexts can reserve SMs for latency-critical kernels.** CUDA 13.1 adds them to the Runtime API. In NVIDIA's test on a 148-SM Blackwell GPU, a latency-critical kernel running next to bulk work dropped from 0.14 ms to 0.007 ms.
- **VisionHOPE is a new backbone with released weights.** Its tiny 26.6M-param model reaches 84.1% ImageNet-1K and 47.9 COCO box AP with Mask R-CNN 1×.

## Top papers

- **VisionHOPE: Visual Backbones as Self-Modifying Learning Systems** — [link](https://arxiv.org/abs/2609.33325). Each layer keeps five coupled memories (content, keys/values, learning rate, retention) that update themselves while they scan the image along rows and columns in four directions. A soft cap and a spectral clamp keep those updates provably non-expansive. The README reports three sizes:
  - **T** (26.6M params, 4.9 GFLOPs): 84.1% ImageNet-1K, 47.9 / 43.1 COCO box / mask AP (Mask R-CNN 1×), 49.4 ADE20K mIoU.
  - **S** (52.9M): 85.2% ImageNet-1K, 49.5 / 44.2 COCO box / mask AP, 50.3 ADE20K mIoU.
  - **B** (91.2M): 85.6% ImageNet-1K, 50.5 / 45.0 COCO box / mask AP, 51.8 ADE20K mIoU.

  This is a recurrent alternative to Mamba-style and linear-attention backbones, and it is trending on HF this week. No throughput numbers are published yet, so benchmark it yourself before treating it as a Swin or ConvNeXt replacement. [code + weights](https://github.com/PSRben/VisionHOPE)
- **Rethinking Long-Video Efficiency: A Joint Allocation Perspective on Frames, Pixels, and Front-End Latency** — [link](https://arxiv.org/abs/2610.04318). At a fixed token budget, many low-resolution frames beat a few native-resolution frames for long-video VLMs, and on hour-long inputs *video decoding* takes most of the wall-clock time. Their training-free LoHi method adds a few high-resolution frames to a dense low-resolution stream. It picks those frames either from codec I-frame metadata or by query relevance over CLIP features. Across three benchmarks it gains 10.6 points over the native-resolution baseline and 5.2 points over the best prior efficiency method, and cuts decode latency by up to 7×. [project](https://sixundong.com/projects/lohi)
- **Tracking Is Not Permanence: What Video World Models Keep of a Hidden Object** — [link](https://arxiv.org/abs/2610.07355). The authors test a frozen V-JEPA 2 predictor on objects that go out of view:
  - **Moving object:** forgotten within 0.3 s.
  - **Object carried inside a container:** not kept at all, even though the encoder can still decode it for 3.5 s.
  - **Fix:** 3k predictor-only fine-tuning steps on synthetic containers raise the permanence belief from 0.05 to 1.00 and IntPhys-2019 from 84.2% to 93.3%.

  VideoMAE keeps almost nothing. This matters if you plan to use video SSL features for tracking through occlusion.
- **From the Drosophila Visual Connectome to General-Purpose Computer Vision** — [link](https://arxiv.org/abs/2610.08418). FlyVision is a backbone modeled on the fruit-fly visual connectome: separate ON and OFF pathways, recurrence, and graph interaction between neuron populations. On ImageNet-1K the 3.7M-param version reaches 66.25% (66.53% with a low-frequency branch), against 69.25% for ResNet18 at 11.7M params. On chest X-ray it beats ResNet18 (92.76% vs 91.56%) with about 4× fewer params. This is not SOTA, but it is an unusual design for very small models.
- **LAO-X** — [link](https://arxiv.org/abs/2610.07326). Adapts a SAM2-based localizer to X-ray scans without human labels. The abstract reports 2–23% mAP gains over SAM2 and X-ray baselines in cluttered scenes, which makes it a useful example of adapting a promptable model to a new imaging modality without annotation.

## GPU / CUDA / PyTorch

- **Evolution of the PyTorch Media Processing Landscape** — [link](https://pytorch.org/blog/evolution-of-the-pytorch-media-processing-landscape/). TorchCodec becomes the one place for image, video and audio decoding and encoding on both CPU and CUDA. torchvision's video I/O is deprecated, and torchvision narrows to transforms. Combined with the LoHi result above, decoding is the step to profile first in long-video pipelines.
- **Control How Your GPU Shares Work with Green Contexts** — [link](https://developer.nvidia.com/blog/control-how-your-gpu-shares-work-with-green-contexts/). Green contexts let one process split the GPU's SMs and work queues into partitions and bind streams to them. CUDA 13.1 exposes this in the Runtime API (`cudaGreenCtxCreate`, `cudaExecutionCtxStreamCreate`). NVIDIA's latency-critical kernel took 0.14 ms on a high-priority stream and 0.007 ms with its own partition.
- **Modernizing Table Batched Embeddings with FBTriton** — [link](https://pytorch.org/blog/modernizing-table-batched-embeddings-with-fbtriton/). Meta replaced its hand-written CUDA embedding kernels with Triton and got a median 1.28× forward speedup, with code that runs on Hopper, Blackwell and AMD. The workload is recommendation models, but it is another data point that Triton can replace hand-written CUDA in production.

## Today's deep read

**Control How Your GPU Shares Work with Green Contexts** — [link](https://developer.nvidia.com/blog/control-how-your-gpu-shares-work-with-green-contexts/).

- **What to read:** the experiment that runs a latency-critical kernel next to bulk work, and the walkthrough of the Runtime API.
- **Why stream priorities fall short:** a high-priority stream only affects which work starts next. Once bulk kernels occupy the SMs, a priority kernel still waits for them, so priority alone does not give you isolation.
- **How it could apply to you:** if one GPU runs a real-time detector next to a tracker, re-ID model or batch embedding job, sketch how you would reserve a fixed slice of SMs for the detector. Measure p99 latency rather than the mean, and weigh what the reserved slice costs the other jobs in throughput.
