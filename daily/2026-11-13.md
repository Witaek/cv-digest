## TL;DR
- **ONNX Runtime 1.32.0 is out (PyPI, today 11:05 UTC).** The Python-visible changes: a new **model package** API (`ModelPackageContext` and friends) for picking a component variant and creating a session from it, and an offline tactic tuner for weight-only `MatMulNBits` GEMMs on CUDA (`python -m onnxruntime.tools.fpa_intb_tune`). - **ORT static QDQ quantization fixes FP16 bias problems.** If an FP16 bias's scale would round to zero or clip in int32, the quantizer now uses an FP32 `DequantizeLinear` followed by a cast to FP16. It also allows FP16 subnormal scales. **If you quantize FP16 ONNX detectors with `quantize_static`, re-quantize: zeroed or clipped biases are a silent accuracy loss.**
- **RF-DETR 1.12.1 is a fixes release.** Compiled or fixed-batch exports now batch at their own size by default, which also fixes the error on finite streamed sources. Drop-path no longer overflows in FP16. NaN pixels and non-finite YOLO labels now raise an error, and invalid training configs are rejected up front. Results don't change; it's a safe upgrade from 1.12.0.

## Models & releases

- **RF-DETR 1.12.1** — [PyPI](https://pypi.org/project/rfdetr/1.12.1/). Uploaded Nov 12, 13:25 UTC. There are no new weights and no metric changes. (1.12.0 was covered Nov 7.)
  - **Batching for fixed-batch runtimes:** with `batch=None`, a compiled snapshot or a fixed-batch export now runs finite sources (directories, globs, videos, streamed or not) in batches of its own batch size. In 1.12.0, streamed sources defaulted to one image per batch, which fails on a batch-4 engine. A short final batch is still refused. Live captures and `.streams` keep one frame per source, and the source count must match the fixed batch size.
  - **Less mask copying:** when every score row passes the threshold, predict no longer gathers the full-resolution mask tensor on the GPU. It copies once during the device-to-host transfer instead. This saves one large GPU allocation per image for segmentation models when few rows are filtered.
  - **FP16 drop-path:** in the DINOv2 backbone, drop-path now masks before scaling and does it in float32 for FP16 inputs. The comment says FP16 "can overflow on a dropped path before multiplication by zero". Drop-path rates are now computed in float64, so a rate just below 1 no longer rounds to 1 and divides by zero.
  - **Stricter inputs:**
    - NaN pixels now raise "values below 0 or NaN". Before, a NaN passed both range checks.
    - YOLO labels with non-finite box or polygon coordinates raise an error naming the file and line.
    - Training configs now validate their ranges: `epochs ≥ 1`, `0 ≤ ema_decay ≤ 1`, `warmup_epochs ≥ 0` and `0 ≤ drop_path < 1`. Before, `epochs=0` raised a `ZeroDivisionError` in the optimizer setup and `drop_path=1.0` produced NaNs.
  - **Mask IoU** uses `reshape` instead of `view`, so non-contiguous mask tensors no longer raise an error during evaluation.
  - **README:** the benchmark charts are now versioned SVGs. The detection chart compares against YOLO11, YOLO26, LW-DETR and D-FINE on COCO and RF100-VL.

## Edge & deployment

- **FP16 bias handling in ORT static quantization (1.32.0):**
  - **The problem:** in QDQ quantization, the bias scale is `input_scale × weight_scale`, and it used to be stored as FP16 for FP16 models. That product can underflow to zero in FP16, or come out too small for the bias to fit in int32.
  - **The fix:** for FP16 biases (except FP8 weights), the quantizer now checks for both cases. If either applies, it computes the scale in FP32, writes an FP32 `DequantizeLinear` and adds a `Cast` to FP16 after it. The comment: "Use FP32 DQ followed by an FP16 cast if scale rounding would erase or clip the bias".
  - **Related fixes:**
    - When the weight scale is enlarged to fit the bias, FP16 rounding can no longer round it back down (`nextafter` toward +∞).
    - FP16 subnormal scales are now accepted. Before, they were reset to 1.0, which wrecked the quantization of small-range tensors.
    - A `beta=0` bias now quantizes to zeros.
  - **What to do:** this hits small-magnitude layers in FP16 models, such as detector heads with tiny activation ranges. If you ship FP16→INT8 QDQ ONNX models, re-run `quantize_static` with 1.32.0 and compare per-layer outputs and mAP against your current artifacts.
- **Dynamic quantization of Gemm (1.32.0):** when `Gemm` is rewritten to `MatMul`, a transposed weight now gets a new initializer (`<name>_Transposed`). Before, the original initializer was overwritten, which broke any other node sharing it. Per-channel `TensorQuantOverrides` are copied to the transposed weight with the axis flipped. The caller's options dict is no longer mutated.
- **`float16.convert_float_to_float16` (1.32.0):** an FP16 tensor feeding several FP32-only or blocked nodes now gets one shared `Cast`, not one per consumer. Shape inference now also works when the model's directory holds external data.
- **Weight-only INT GEMM tuning on CUDA (1.32.0):** `onnxruntime.tools.fpa_intb_tune` profiles the fpA_intB kernels behind `MatMulNBits` for the M values you list (e.g. `1,8,…,2048`). It writes a `<prefix>.matmulnbits_fpa_intb.tsv` tactic cache that later sessions reuse. The cache only works on the same GPU, SM, CUDA runtime and ORT version. This mostly matters for 4-bit LLM and VLM decoders, not convolutional detectors.

## Today's deep read

**How an FP16 bias gets lost in INT8 QDQ, and the 1.32.0 fix** — [onnxruntime 1.32.0 wheel on PyPI](https://pypi.org/project/onnxruntime/1.32.0/#files) (`quantization/qdq_quantizer.py`, `base_quantizer.py`, `quant_utils.py`).

- **What to read:**
  - In `qdq_quantizer.py`, the new block before `quantize_bias_static_impl`. It computes `bias_scale_fp16` and switches to FP32 if any scale is 0 or any `|bias| > int32_max × scale`.
  - The new `Cast` insertion after the bias `DequantizeLinear`.
  - In `base_quantizer.py`, the `min_bias_scale` clamp (`|bias| / int32_max × 1.0001`).
  - In `quant_utils.py`, the switch from `finfo.tiny` to `smallest_subnormal` for FP16.
- **Why it matters:** a typical activation scale (~1e-3) times a per-channel weight scale (~1e-5) is about 1e-8. That is below FP16's smallest subnormal (~6e-8), so the bias scale rounds to 0 and the bias is lost or clipped. The model still runs, mAP just drops a little, and nothing warns you. This is the same pattern as this week's Ultralytics changes (Nov 11–12), which kept detector heads in float under INT8: the damage happens at the head, in layers with small ranges.
- **How it could apply to you:**
  - If your pipeline is PyTorch → ONNX FP16 → ORT `quantize_static` → TensorRT, OpenVINO or QNN, look for `DequantizeLinear` nodes on biases with FP16 scales of 0 in your current models. A short script over the initializers will find them.
  - After re-quantizing with 1.32.0, the bias DQ nodes for affected layers will be FP32 with a cast after them. Check that your target EP fuses that pattern rather than falling back to CPU for it.
  - If you build FP32 models and cast to FP16 after quantizing, this fix doesn't apply to you. The safer order is still to quantize from FP32.
