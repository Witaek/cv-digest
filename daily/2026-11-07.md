## TL;DR
- **RF-DETR 1.12.0 is a big deployment release.** It adds calibrated INT8 export for TensorRT, ONNX and OpenVINO. On TensorRT 11.4, INT8 runs 1.08–1.42× faster than FP16 on an RTX 5070 and a T4, and costs 0.27–0.66 box AP on detection. LiteRT CPU latency is roughly halved, ExecuTorch XNNPACK latency drops 35–55%, and CUDA-graph inference makes Nano 2.5× faster end to end on an L4. There are breaking API changes.
- **Ultralytics 8.4.204 adds native tiling (`tile=`)** to train, val, predict and track. It cuts 20%-overlap windows in source pixels and merges detections, masks, keypoints, semantic maps and depth back into the full image. That covers what many people use SAHI for, for small objects in large frames.
- **A Core ML fix in RF-DETR quietly restores about 3 AP on the Apple Neural Engine.** FP16 bundles now keep deformable-attention resampling on the CPU: Nano goes from 45.06 to 48.04 AP under `CPU_AND_NE`, at +1.9 ms per image. Re-export your RF-DETR Core ML models.

## Models & releases

- **RF-DETR 1.12.0** — [PyPI](https://pypi.org/project/rfdetr/1.12.0/), [changelog](https://github.com/roboflow/rf-detr/blob/develop/CHANGELOG.md). Uploaded Nov 6. The headline items:
  - **New `RFDETRInference` predictor.** One API serves a live model, a checkpoint, or any full export. Exports now carry versioned metadata (embedded in ONNX files, written as a `.rfdetr.json` sidecar for other formats) so that pre- and post-processing can't drift from what the model was trained with. It reads video, RTSP/HTTP streams, cameras, globs and screen capture, with `stream=True`. Install `rfdetr[stream]` for those sources.
  - **Per-class thresholds** via `ClassThresholds({"person": 0.35, "traffic light": 0.6}, default=0.5)`.
  - **Faster eval:** `eval_backend="hotcoco_streaming"` matches each validation batch as it arrives, with metrics bit-identical to batch evaluation.
  - **Breaking changes:**
    - `RFDETR.inference()` now returns a separate predictor, and the default compile backend now depends on the device: CUDA graph on CUDA, inductor on MPS, TorchScript elsewhere.
    - FP16 Core ML bundles now return float32 outputs and target iOS 15.
    - Kornia GPU augmentation now refuses `multi_scale="per-sample"` or `square_resize_div_64=False`. With those settings, smaller images were silently trained on shrunken boxes, so check older runs that used them.
    - `rfdetr[onnx]` no longer pulls in `polygraphy` or `onnx_graphsurgeon`.
    - Weights now download from `repo.roboflow.com`, so add that host to any firewall allowlist.
- **Ultralytics 8.4.204** — [PyPI](https://pypi.org/project/ultralytics/8.4.204/). Uploaded Nov 6, 21:34 UTC. From the 8.4.203→8.4.204 sdist diff:
  - **`tile=True` (window size = `imgsz`) or `tile=<int>` (window size in source pixels).** `tile_windows` lays out windows with 20% overlap, with the last row and column aligned to the image edge.
  - **Training** turns every window into its own sample. The RAM cache keeps one copy of each source image, not one per tile.
  - **Validation** gathers all tiles of a source image, merges them with `ops.merge_tiles`, and scores against the *original* full-image targets. So mAP stays comparable to untiled runs.
  - **How the merge works:** boxes, masks and keypoints go through a class-aware NMS pass across tiles. Semantic maps keep, for each pixel, the tile where that pixel is farthest from the edge. Depth is blended with weights that fall off toward tile edges.
  - **Prediction and tracking** support tiling too, including with exported models.
  - **Also:** FastSAM text prompts now use a TorchScript `clip_b32_datacomp.ts` instead of the `clip` package.
- **transformers 5.22.2:** a patch to distributed-training and chat-template utilities only. Nothing vision-related.
- **Release check (PyPI):** unchanged for torch 2.15.0, torchvision 0.29.2, timm 1.0.31, supervision 0.31.5, Roboflow Inference 1.8.4, SAHI 0.14.0, ONNX Runtime 1.31.1, ONNX 1.23.2, TensorRT 11.4.0.106, OpenVINO 2026.4.1, LiteRT 2.3.0, Triton 3.9.0, torchao 0.18.0, flash-attn 2.8.3.post2, Kornia 0.9.0, Model Optimizer 0.48.0 and ExecuTorch 1.6.0 (whose release notes we still couldn't read). ## Edge & deployment

All numbers are from the RF-DETR 1.12.0 changelog.

- **TensorRT INT8 for RF-DETR** — `export(format="tensorrt", quantization="int8", calibration_data=...)`.
  - **How the INT8 export works:**
    - TensorRT can't run the 3-channel patch embedding as an INT8 convolution, so it is exported as a matrix multiply.
    - Backbone LayerNorm outputs are smoothed (SmoothQuant), and backbone MLP biases are corrected for the mean shift INT8 introduces. Both are folded into the weights.
    - Mask and keypoint heads stay FP16.
  - **Results** on TensorRT 11.4, with all 5000 COCO val2017 images, calibrated on 128 train images:
    - Detection (N/S/M/L) loses 0.50 / 0.36 / 0.65 / 0.27 box AP on a T4.
    - Across tasks (box, mask and keypoint AP), batch-1 losses are 0.27–1.01 AP.
    - Engines are 24–59% smaller.
    - Speedups over FP16 are 1.11–1.42× on an RTX 5070 and 1.08–1.41× on a T4 (with a CUDA graph), at batch 1, 4 and 8.
  - **Limits:** no dynamic batch.
- **Static INT8 for ONNX and OpenVINO (via NNCF)**: only `MatMul`/`Gemm` run in INT8. ONNX Runtime's default op coverage cost 9.65 mAP on Nano and 12.14 on Small, versus 2.65 and 2.67 for this matmul-only setup (on a 500-image val subset). The changelog expects about 3× smaller files and about 1.4× faster CPU inference at batch 1. That accuracy drop is far larger than TensorRT's, so validate on your own data.
- **LiteRT CPU latency roughly halved.** Deformable-attention sampling used to fall outside the XNNPACK delegate; it's now rewritten so XNNPACK runs it. Median latency on Xeon Haswell: Nano 168.6 → 78.1 ms, Large 431.1 → 256.8 ms. On M4 Max: Nano 78.4 → 38.5 ms. mAP changes by ≤0.01.
- **ExecuTorch XNNPACK:** attention now stays inside the delegate (on Nano, partitions drop from 87 to 57). On the pinned ExecuTorch 1.3.1, M4 Max CPU: Nano 49.3 → 31.8 ms, Large 201.7 → 91.5 ms. mAP changes by ≤0.01.
- **Core ML:**
  - `coreml_neural_engine=True` adds a Neural Engine-friendly graph.
  - Separately, the FP16 accuracy fix: under `CPU_AND_NE` on an M3 Pro, Nano goes 45.06 → 48.04 AP and Small 50.70 → 52.76 AP. The cost is batch-1 p50 latency: Nano 10.8 → 12.7 ms back to back.

## GPU / CUDA / PyTorch

- **CUDA-graph inference in RF-DETR.**
  - **PyTorch path:** `RFDETR.inference()` now captures a CUDA graph by default on CUDA. On an L4, RF-DETR Nano FP16 at batch 1 goes from 9.72 to 3.88 ms median end to end (2.5× throughput), with identical COCO AP (0.4802). Capture adds about 29 MiB of GPU memory and about 7 s of setup. It needs a fixed batch size and resolution.
  - **TensorRT path:** `TRTInference(cuda_graph=True)` brings Nano from 1.65 to 0.99 ms at batch 1 on an RTX 5070. The gain shrinks to 1.05–1.09× at batch 8, so this matters most for batch-1 streaming. It isn't thread-safe.

## Today's deep read

**RF-DETR 1.12.0's INT8 TensorRT path** — [changelog](https://github.com/roboflow/rf-detr/blob/develop/CHANGELOG.md) (entries #1560, #1583, #1547), [CUDA export cookbook §8.1](https://rfdetr.roboflow.com/latest/cookbooks/export-cuda/#81-benchmark-for-the-docs-tables).

- **What to read:**
  - How the INT8 export handles the patch embedding and SmoothQuant, and the bias correction. These are the general tricks for keeping a DINOv2-style ViT backbone accurate under INT8.
  - The ONNX/OpenVINO entry: it explains why quantizing every op is worse than quantizing only matmuls on these models, at 9.65 versus 2.65 mAP lost.
- **Why it matters:** INT8 on transformer detectors has usually cost several AP. A sub-1-AP loss with a 1.1–1.4× speedup changes the latency budget of ViT-based real-time detectors on T4/Orin-class hardware.
- **How it could apply to you:**
  - **Benchmark first:** reproduce §8.1 on your GPU before trusting the numbers.
  - **Calibrate on your own data:** use 128–512 images from your deployment domain, not COCO, and compare per-class AP. Small objects usually suffer first.
  - **For batch-1 video,** try a CUDA-graph replay on top. It needs a static-shape engine, and each stream needs its own runtime because it isn't thread-safe.
  - **If you're on YOLO with small objects,** run 8.4.204's `tile=` validation against your current SAHI pipeline. Because tiled val scores against full-image targets, the two mAP numbers are directly comparable.
